Read README plus selected source/documentation at the exact commits below. No external code executed or copied into GeoCrop; this is a capability/design comparison, not an empirical speed/accuracy benchmark or an exhaustive ecosystem review.

| Project | Inspected HEAD (commit date) | Verified capability and GeoCrop implication |
|---|---|---|
| sits | `dd33dfc0d32aa3f8a0f12804841c7cb80ae6c082` (2026-01-15) | The README defines regular/multisource data cubes, sample QC with self-organising maps, model fitting/classification, Bayesian smoothing, uncertainty and active learning. `sits_accuracy.R` distinguishes classification accuracy and Olofsson-style area-weighted accuracy on validation observations. `sits_uncertainty.R` has entropy, least-confidence and margin uncertainty plus explicit `multicores`/`memsize` budget controls. GeoCrop already implements corresponding probability uncertainty, area estimators, label suspicion and active-learning ranking; those are not novel advantages over sits. GeoCrop's useful emphasis is explicit parcel-declaration evidence and spatial design. |
| FORCE | `637363535752122c7e8ed95a9b834f0507eb1d70` (2026-09-02) | Official README documents an archive/data-cube processing engine for Landsat/Sentinel-2 and non-native sources. The time-series interpolation guide explicitly warns that interpolated estimates become less reliable when nearby valid observations are distant; TSA format separates acquisition stacks (`TSS`), interpolation (`TSI`), metrics and phenology. Trend products expose fit residuals and observation counts. GeoCrop currently emits smoothed samples/phenology/harmonics but no per-pixel temporal-support output, so users cannot easily distinguish well-observed from heavily imputed signatures. |
| blockCV | `51e6903fe652411248aa20937c80b122e5e12e09` (2026-10-14) | Official README/source supports blocks, buffering, spatial/environmental groups and nearest-neighbour distance matching. `cv_distance.R` compares test-to-training nearest-distance distributions against target prediction-domain distances; it returns per-fold quantiles and Wasserstein-1 mismatch. `cv_similarity` reports feature-space novelty. GeoCrop's new buffer and minimum-distance reporting are useful but do not yet describe whether test separation resembles deployment or how much each fold extrapolates. README specifically cautions that ranges from raw response/covariates are exploratory proxies; residual autocorrelation is a different diagnostic. |
| MAPIE | `f1cc3d07460b2d7198f557d40d60cd563c51822b` (2026-10-19) | `SplitConformalClassifier` explicitly separates estimator `fit`, `conformalize` on held-out data and `predict_set`; its runnable documentation splits train/conformalize/test subsets and uses `prefit=False`. GeoCrop's present `train` temperature-fits pooled OOF labels, quantile-fits on those same polygons and then deploys a model refitted on all training data. Existing metadata now honestly says empirical/no guaranteed split-conformal coverage. The high-impact capability gap is a real frozen-predictor calibration path rather than more classifier choices. |

## Prioritised implementation suggestions

1. **Add a held-out calibration workflow tied to the exact deployed model.** Accept independent calibration `Samples`, validate ordered feature names/classes/polygon IDs, reject overlapping training IDs/support and label conflicts, leave calibration polygons out of fitting and tuning, and use the same fixed estimator and temperature at inference. If temperature is estimated from this calibration set, it must be fixed using a separate probability-calibration partition before conformal-score calibration; simply fitting both on the same labels recreates the current issue. Store explicit model fingerprint, calibration inputs, counts, class fallback, method and assumptions. A spatial holdout reduces leakage but does not itself establish exchangeability or operational coverage. Expose independent coverage/set-size assessment on a third untouched set. Unit/integration tests should prove calibration rows cannot reach model fit, model is not refit after score calibration, changed model artifacts invalidate attached calibration, and sparse classes are conservative/explicit.

2. **Expose temporal-support quality alongside the reconstructed features.** Preserve per-index observed-count, occupied-bin fraction, first/last supported time, longest unobserved gap and fitting RMSE in a separate quality raster + JSON summary, so a QC raster does not accidentally become a classifier feature merely by being stacked. Optional configurable gap/coverage masks should affect phenology/prediction only when opted in, with counts/reasons recorded. Test long central vs boundary gaps, same-day duplicates, zero valid observations, partial sensor coverage and differing observation quality. FORCE provides the important evidence/interpolation distinction; this is an independent implementation proposal, not a claim of exact product parity.

3. **Extend fold diagnostics from a single minimum to deployment-aware summaries.** Add per-fold nearest-test/train distance quantiles, class/polygon/sample support and feature novelty; optionally sample target-grid points deterministically and compare their nearest-reference distances with held-out distances. Report distributions/mismatch descriptively rather than automatically declaring one fold design valid. Retain fold membership and seed in outputs for repeatable ablation. blockCV offers a reference design. A useful first increment needs only existing SciPy `cKDTree`, NumPy and GeoCrop sample/grid support.

4. **Correct autocorrelation wording.** GeoCrop `spatial.py`/uncertainty docs currently describe the first-PC variogram range as a defensible lower bound for block size. The actual first PC is a covariate proxy; it neither establishes residual dependence nor guarantees adequate block size. Label it exploratory, permit residual/error input and record which variable drove the recommendation. This is a small documentation/API clarification worth including alongside the new calibration or quality feature.

No claim is made that these changes make GeoCrop universally best. A meaningful comparison would fix study data, independent spatial/temporal test sets, hardware/runtime budgets, algorithms and scoring protocol, then report measured parcel outcomes, calibration, coverage, throughput and failure recovery.
